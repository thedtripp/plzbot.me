# Episode 6 — verification log

| Claim | Primary source | Corroborating source |
|---|---|---|
| The TLS ClientHello is sent unencrypted and lists cipher suites/extensions in client-chosen order | [RFC 8446 §4.1.2, The Transport Layer Security (TLS) Protocol Version 1.3](https://www.rfc-editor.org/rfc/rfc8446#section-4.1.2) (IETF, primary) | Reused from this project's own `public/docs.html`/`docs/TLS_CAPTURE.md`, already-reviewed |
| JA3 was created at Salesforce in 2017 by John B. Althouse, Jeff Atkinson, and Josh Atkins; hashes five ClientHello-derived fields (TLSVersion, Ciphers, Extensions, EllipticCurves, EllipticCurvePointFormats) via MD5 into a 32-character fingerprint; the Salesforce project is no longer actively maintained | [Salesforce Engineering Blog — "TLS Fingerprinting with JA3 and JA3S"](https://engineering.salesforce.com/tls-fingerprinting-with-ja3-and-ja3s-247362855967/) (primary, original authors) | [salesforce/ja3 on GitHub](https://github.com/salesforce/ja3) |
| Node's `tls` module does not expose raw ClientHello bytes through any public API; the naive peek-and-`unshift()`-then-hand-off approach hangs the handshake because `TLSSocket` re-parents the underlying handle rather than reading it through ordinary stream events | First-party: this project's own `docs/TLS_CAPTURE.md`, documenting a bug reproduced and diagnosed during this project's original build (confirmed via curl timeout / `socket hang up`, and by confirming the identical technique works fine against a plain non-TLS `http.Server`) | — (internal engineering finding, already reviewed) |
| This project's `FrontProxy` architecture (peek ClientHello on an untouched socket, then open a separate loopback connection to the real TLS server) works around the above, correlating connections via a self-chosen local port | First-party: `src/server/tls-capture/frontProxy.ts` and `docs/TLS_CAPTURE.md`, verified during this project's original build against real curl requests over HTTP/1.1 and HTTP/2 | — |
| curl and Python's `requests` produce different JA3 hashes against the same server with equivalent headers, because they link different TLS libraries | First-party: this project's own probe run (`probe-output/2026-08-30T00-42-05-880Z/`) — `curl_default_.json` shows JA3 hash `4f2655722e...`, `python_requests_default_.json` shows `4b510481e2...` | — |
| JA4 was created by John Althouse under FoxIO as a successor to JA3, using an `a_b_c` format where section `a` is human-readable (packing version/SNI-presence/cipher-count/extension-count/ALPN into ~10 characters) and sections `b`/`c` are hashes | [FoxIO Blog — "JA4+ Network Fingerprinting"](https://blog.foxio.io/ja4+-network-fingerprinting) / [Medium — same, John Althouse](https://medium.com/foxio/ja4-network-fingerprinting-9376fe9ca637) (primary, original author) | [FoxIO-LLC/ja4 README on GitHub](https://github.com/FoxIO-LLC/ja4/blob/main/README.md) |
| RFC 8701 reserves 16 GREASE values of the form `0xXAXA` for TLS implementations to advertise at random, specifically to prevent servers/middleboxes from breaking on values they haven't seen before | [RFC 8701, Applying GREASE to TLS Extensibility](https://www.rfc-editor.org/rfc/rfc8701.html) (IETF, primary) | This project's own `src/server/tls-capture/grease.ts`, already implementing exactly this value set |
| JA4 is a best-effort implementation in this project, not independently validated against FoxIO's reference implementation on a large traffic corpus; JA3/JA4 require the app itself to terminate TLS (unavailable behind a CDN/load balancer that terminates TLS upstream) | First-party: `docs/TLS_CAPTURE.md` "Limitations, honestly stated" section, and header comment in `src/server/tls-capture/ja4.ts` | — |
