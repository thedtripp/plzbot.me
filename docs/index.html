The whole product, in plain terms

When a program connects, we answer three questions.

Not a person anymore — that’s the shift. The visitor is often an AI agent booking, buying, comparing prices, or pulling data for someone. Today you can’t tell a customer’s helpful agent from a scraper, a fraud bot, or a broken agent stuck in a loop. So we check:

01

What is it, really?

We fingerprint the actual client — TLS (JA3/JA4), HTTP/2 settings, header order, Client Hints, and SDK signatures like x-stainless-lang. A Python httpx script claiming to be Chrome doesn’t look like Chrome. We can tell.

02

Is it who it claims to be? V2 ROADMAP

Agents increasingly arrive with a name tag: Web Bot Auth and RFC 9421 HTTP message signatures. The v2 plan: verify the signature, then check whether the detected stack matches the claim. Claimed identity, proven — or flagged as a lie.

03

Is it behaving itself? V2 ROADMAP

Same fingerprint, seen across requests, becomes a stable identity — the persistence layer on the v2 roadmap. That unlocks cadence, endpoint sequences, per-agent budgets, and loop detection — the agent making the same call 10,000 times gets stopped before the bill does the talking.

Evidence, not vibes

One fingerprint document. Every signal, on the record.

plzbot started as an open fingerprinting engine that returns evidence, not a black-box bot-or-not score. That fingerprinting core exists today. The identity, behavior, and verdict layers below are the v2 build now in development — and the design goal is that you see exactly why a visitor was allowed, throttled, or blocked, so your auditors can too.

TLS

JA3 & JA4 from the real ClientHello

Captured where TLS terminates, not guessed from headers. Works for browsers and for raw SDK clients — most agent traffic never opens a browser at all.

HTTP

Header order, HTTP/2 & Client Hints

The order headers arrive in, the SETTINGS frame a client sends, the hints it offers. Hard to fake consistently, easy to match against a known stack.

SDK

Agent-stack corpus — v2 roadmap, step one

The first v2 build task: record known fingerprints for CPython ssl & httpx, Go net/http & uTLS, Node undici, Rust reqwest — plus OpenAI / Anthropic Stainless headers that name the exact library and version.

ID

Declared identity, verified — v2 roadmap

Web Bot Auth signature checks, rarity scoring, and a stable client identity derived from the fingerprint plus any presented token. The schema already has slots for these; v2 fills them in.

WEB

Browser signals, when there is a browser

Canvas, WebGL, fonts, audio, and automation indicators for the agent traffic that does drive a real browser.

Policy lives outside the evidence. plzbot stays pure; your rules — allow, throttle, challenge, deny — sit in a separate layer and consume a signed verdict JWT.

One honest constraint, by design: JA3/JA4 only exist where plzbot terminates TLS itself. Behind a TLS-terminating platform, those signals go dark — so the agent version sits at the TLS endpoint, as a proxy or at your edge.

Allow

Verified agent, known stack, normal behavior. Let it work — it’s your customer’s agent, doing what your customer asked.

WHEN · signature ✓ · stack matches claim · loop score low

Throttle

Real client, no proven identity — or just moving too fast. Give it a per-agent budget instead of a ban.

WHEN · unsigned · unknown SDK · cadence above budget

Challenge

Claim and evidence disagree. Ask it to prove itself — sign the request, slow down, or identify its operator.

WHEN · claims Chrome, fingerprints as Python

Block

Forged signature, known scraper stack, or a loop burning compute. Out — with the evidence attached to the log line.

WHEN · bad signature · loop_score > 0.9 · blocklisted stack

Questions

Asked at every door.

Isn’t this what Cloudflare and DataDome do?

At the top of the market, yes — edge bot management and enterprise agent-trust suites, sold through sales teams on annual contracts. plzbot.me lives one layer down: a developer-first fingerprinting and identity API, self-serve, aimed at the API and MCP operators those vendors don’t call back. Same problem, different door.

My agents are just SDK clients, not browsers. Does this still work?

That’s the main case. The server half fingerprints any HTTP client — curl and requests get full documents today. TLS, HTTP/2, header order, and Stainless SDK headers identify Python, Go, Node, and Rust stacks without a browser ever being involved. Browser signals (canvas, WebGL, fonts, audio) are the bonus layer, not the foundation.

What is Web Bot Auth, and why does verification matter?

It’s how an agent proves who it is: the operator signs requests (RFC 9421 HTTP message signatures) with a key tied to its identity. A claim anyone can type into a User-Agent is worthless. A valid signature that also matches the detected stack is an ID check. plzbot verifies both halves — the signature, and whether the client in front of us matches the name on the tag.

Where does plzbot have to sit in my stack?

At the TLS endpoint. JA3/JA4 come from the TLS ClientHello, so if a platform terminates TLS before plzbot sees the connection, those signals go dark. In practice: proxy mode in front of your API or MCP server, or at your own edge. Your app then consumes headers or a signed JWT — policy stays in your layer.

Do you store my traffic?

We store fingerprint documents and the stable identities derived from them — that persistence is what makes recognition, budgets, and loop detection possible. We don’t need your payloads to fingerprint a client, and the evidence record for each decision is exportable to you for audits.
